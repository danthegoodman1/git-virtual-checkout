# Virtual git checkouts over FUSE: feasibility

Scoped 2026-11-14 against GitHub, git 2.53.0, Linux 7.0. Every number below
comes from a run on this machine unless marked otherwise; the appendix lists the
commands.

## Verdict

A virtual checkout of a GitHub repo, used with stock git, is feasible today.
The main discovery is that the fastest object API GitHub offers is its own git
endpoint, not REST. GitHub's smart-HTTP server supports partial clone
(`filter`), shallow fetch, and fetching any reachable object by id. Git's
promisor-remote machinery already fetches missing objects lazily from it, and
it sits outside the REST quota. REST and GraphQL still matter, but only for
metadata the git protocol lacks: blob sizes, blame, path history, and
merge-bases.

| Question | Answer |
|---|---|
| Instant checkout? | Yes, with progressive listing. The Linux kernel's blobless depth-1 fetch is 3.3 MB and has taken 1.1–15 s, depending on GitHub's cache; with every blob size from the tree API (7.7 MB of gzipped JSON), the whole bootstrap ran 4.1–8.4 s (median 4.4 s) against 40 s for `git clone --depth=1`. git/git's fetch takes 0.9 s. Directories can list before the full listing lands, one tree-API call each, and files fetch on first read. |
| `git status`, `diff`, `add`, `commit`? | Yes, if the daemon writes the index itself, with stat data matching what FUSE reports, and answers git's fsmonitor hook from its own write log. |
| New commit hashes? | Git computes them locally. A commit needs blob ids for unchanged files, which the index already holds, not their contents. |
| Push without full history? | Yes. Pushing a new commit from a depth-1 blobless clone made zero lazy fetches, and the remote accepted it. |
| Git LFS? | Yes, with no smudge step and no git-lfs install. FUSE shows LFS content in place of each pointer, sized from the pointer and fetched by byte range. gvc acts as the LFS filter for `git add` and uploads new objects on push. |
| `git log` without a full clone? | Yes, with one of two methods. Small and medium repos can fetch all commits and trees in the background (git/git: 117 MB in 6 s). Kernel-scale repos need a lazy object store that serves commits on demand. Either way, git reads objects; it has no "log" request that the API could answer directly. |
| `git log -- path`, `blame`, `log -p`? | They work. Speed depends on fetching what the command needs in one batch. Lazily, `git blame Makefile` on git/git made 944 sequential fetches and took 282 s. Planned from local trees and prefetched in one batch, it took 3 s with identical output. GraphQL blame took 3.7 s and matched on all 4,146 lines, but it covers only pushed commits. |
| Switching commits? | Plain `git switch` works, and its cost grows with the diff (one batched fetch for the changed blobs). A `gvc switch` command can swap the lower layer and rewrite the index instantly. |
| Worktrees? | Plain `git worktree add` works but downloads and writes every file. A `gvc worktree add` command can create a virtual worktree instantly that shares the object store and blob cache. |

## How git and the network split the work

```
                ┌──────────────── gvc daemon ────────────────┐
 working tree   │  FUSE overlay                              │
 (FUSE mount) ──┤    lower: tree @ HEAD (immutable, by oid)  │
                │    upper: local edits, whiteouts, renames  │
                │  blob cache (content-addressed, shared)    │──┐
                │  fsmonitor answers (from the write log)    │  │   Backend interface
                └────────────────────────────────────────────┘  ├─► git protocol v2 (universal, exact bytes)
 .git (real dir)                                                │   GitHub REST/GraphQL (sizes, blame,
   HEAD, refs, config, hooks                                    │     path history, merge-base, tarball)
   index      ← generated by gvc                                │
   objects/   ← blobless partial clone, promisor = origin ──────┤
   objects/info/alternates → lazy object store (Phase 6) ───────┘
```

Git keeps doing what it does well: refs, the object model, hashing, merging,
and the push protocol. The daemon owns three jobs that git can't do for a
virtual tree:

1. It presents the working tree and records every write.
2. It generates an index that git trusts without reading file contents.
3. It tells git which paths changed, so git skips stat-ing the whole tree.

The filesystem logic is platform-neutral Rust. A `Filesystem` trait in
`gvc-vfs` carries node ids, attributes, errno values, directory entries and
completion-style replies, all types a C ABI can carry. The working tree and the
lazy object store implement it, and a thin adapter serves it over FUSE. On
macOS, an FSKit extension written as a Swift shim over the same crates serves
it there.

### Bootstrap (`gvc clone`)

1. Run `git clone --filter=blob:none --depth=1 --no-checkout`. This fetches one
   commit plus every tree at HEAD and no blobs. Linux has 97,371 paths, 6,337
   directories, and 3.2 MB of trees.
2. Get blob sizes from `GET /git/trees/{sha}?recursive=1`. The git protocol
   carries no object sizes (GitHub advertises no `object-info`), and FUSE needs
   correct `st_size` before any read. The recursive call truncates at 100,000
   entries or 7 MB; for Linux it stopped at 71,474 entries after 2.3 s. To fill
   the gaps, call `recursive=1` again on each truncated subtree. For Linux the
   whole walk takes 26 calls and 3.8–4.3 s with gzip, so a lookup waits only on its own
   directory: a directory not yet listed comes from one non-recursive call
   while the rest loads.
3. Write `.git/index` directly, with mode, oid, path, a cache-tree extension,
   and synthetic stat data: a fixed past mtime, size from step 2, and stable
   inode numbers. Set `core.checkStat=minimal`, `core.trustctime=false`,
   `core.untrackedCache=true`, `core.fsmonitor=<gvc hook>`, `gc.auto=0`, and
   `maintenance.auto=false`.
4. Mount FUSE on the working directory. Steps 2 and 4 can run during step 1.
5. In the background, fetch history: `git fetch --unshallow --filter=blob:none`
   for repos where that is cheap (see "History" below).

### Working-tree FUSE layer

- **Lower layer.** The lower layer is the tree at HEAD. `readdir` and
  `getattr` are answered from memory. On first `read`, the daemon fetches the
  blob by oid into the shared cache. A single file comes from
  raw.githubusercontent.com in 20 ms (CDN hit) or 200 ms (miss), or from a
  git-protocol fetch in ~0.25 s. Lower-layer content never changes, so set
  `FOPEN_KEEP_CACHE` and long entry and attr timeouts.
- **Upper layer.** Edits copy up into a hidden local directory. Opening with
  `O_TRUNC` skips the fetch; any other write-open fetches first. Deletes become
  whiteouts. Keep the overlay as a path table in the daemon rather than an
  overlayfs-style directory tree, which makes directory renames cheap. Use FUSE
  passthrough (Linux 6.9+) so upper files read and write at native speed.
- **Special entries.** Symlinks (mode `120000`) store the link target as blob
  content, so prefetch every symlink blob in one batch at clone time. Mode
  `100755` sets the execute bit. Submodules (`160000`) appear as empty
  directories, as they do in a fresh clone.
- **Re-basing.** After `post-checkout`, `post-merge`, and `post-rewrite`, point
  the lower layer at the new HEAD tree and drop upper files whose content now
  matches the lower blob. This keeps the upper layer the size of your real
  changes.

### Index and status

`git status` does three things. It refreshes the index by lstat-ing every
tracked file, it compares the index to the HEAD tree, and it scans directories
for untracked files. On a virtual tree, each step must be served without
reading file contents:

- **Stat matching.** Git reads a file only when the index stat data disagrees
  with `lstat`. Under `checkStat=minimal`, that means mtime seconds, size, and
  mode. Because the daemon reports the same values it wrote into the index,
  clean files stay clean without a fetch. File mtimes must predate the index
  file's mtime, or git re-hashes them as "racily clean."
- **fsmonitor.** With `core.fsmonitor` pointing at a gvc hook (protocol v2),
  git skips lstat for every entry the hook doesn't name. The daemon knows every
  write, so its answer is exact. Git's built-in fsmonitor daemon reports "not
  supported on this platform" on Linux; the hook interface works everywhere.
- **Index–HEAD comparison.** This step needs only trees, which the bootstrap
  already fetched.

### History

Git asks for objects, never for "the log." Making history appear present has
three levels:

1. **Background hydration (Phase 4).** Fetch all commits and trees with
   `git fetch --unshallow --filter=blob:none`. On git/git that is 117 MB in
   6 s, after which `git log -- path` runs in 0.25 s with no fetches.
   Commits-only (`--filter=tree:0`) is 37 MB in 3 s, but `git log -- path`
   then lazily fetches one tree per commit: 31 fetches and 12.7 s for five
   results. Prefer blobless. Until hydration finishes, the repo is shallow, so
   `git log` stops at HEAD and `merge-base` across the boundary fails.
2. **A lazy object store (Phase 6) for repos too large to hydrate.** Point
   `.git/objects/info/alternates` at a second FUSE mount that materializes any
   loose object (`xx/yyyy…`) on lookup. The repo then has no shallow boundary,
   and commits arrive on demand. When commit C is requested, the store also
   fetches C's next N ancestors in one request (`want C` with `deepen N` and
   `filter tree:0`). Tracing git shows this approach is workable:
   - Git opens `objects/xx/<38 hex>` directly by path, so a FUSE lookup can
     block, fetch, and return the object.
   - When writing new objects, `git commit` checks for each new tree and commit
     in the alternate with `access(F_OK)`. The store must answer those with
     ENOENT and no network call. Rule: resolve only ids referenced by a ref or
     by an object already served. Every other id gets ENOENT.
   - `git log --oneline` reads the `objects/xx/` directories to compute unique
     abbreviations. The store can list only what it holds, so set
     `core.abbrev=12`. Short SHAs for commits not yet local won't resolve; to
     support them, resolve through the API (`GET /commits/{short}`) in a gvc
     command.
   - `git gc` repacks with `-l` and leaves alternate objects alone. `git fsck`
     and `rev-list --objects --all` walk everything and would hydrate the repo.
3. **Command-aware prefetch.** A FUSE request carries the caller's pid, and
   `/proc/<pid>/cmdline` shows `git log -p` or `git blame foo.c`. The store
   can prefetch accordingly: a commit range, or every version of one path.
   For blame, plan with `git log --full-history -m --raw -- <path>` over local
   trees, which lists every blob version blame can read. On git/git's Makefile
   that was 3,481 blobs, fetched in one 0.9 s request; `git blame` then ran in
   0.6 s with zero fetches. The plan must be a superset: blame walks side
   branches that `git log`'s default history simplification prunes, so a
   `git log --follow` plan missed 944 blobs. GitHub's path-history endpoint
   returns the simplified list and has the same gap. Planning needs trees for
   the history, so it follows blobless hydration (level 1) or tree readahead
   (level 2).

**Answering from the API.** GitHub's GraphQL blame for git/git's Makefile
matched local `git blame` on all 4,146 lines, in 3.7 s. It sees only pushed
commits and takes no options (`-w`, `-M`, `-C`, `--ignore-rev`). Stock
`git blame` can't call it, because git computes blame from objects and git
aliases can't shadow built-in commands. Use it for a `gvc blame` command or an
editor integration.

**Serving objects from REST/GraphQL instead of the git protocol.** It is
possible but lossy, so verify each object's hash and fall back on a mismatch.
GraphQL's `GitTimestamp` keeps the timezone offset, and rebuilt commits matched
byte-for-byte on three of three git/git commits (after restoring the trailing
newline GraphQL strips). Two GitHub-signed cli/cli merges also matched, once
the `gpgsig` header was rebuilt from `signature.payload` and
`signature.signature`; GraphQL trims a trailing blank line from the armor, so
the rebuild tries both forms. It failed on a Linux merge, because the API omits
the `mergetag` header. REST dates arrive in UTC (`…Z`), which loses the offset that
the hash covers. Treat the git protocol as the source of truth and the APIs as
accelerators for queries.

### Switching, merging, rebasing

- `git switch`, `merge`, and `rebase` all work unmodified. `unpack_trees`
  batches missing blobs into one fetch: a full 4,875-file checkout of git/git
  made one fetch. Git then writes the changed files through FUSE, and the
  post-checkout re-base folds them back into the lower layer.
- Avoid `git checkout <rev> -- <path>` and `git restore --source`. They fetch
  one blob per file: 338 fetches in 300 s for one directory of the kernel.
  Fixes: a gvc prefetch before the command, or a lazy store that batches.
- Git has no pre-checkout hook, so an instant jump between distant commits (for
  example, Linux `v5.0` to `master`) needs `gvc switch <rev>`. For a clean
  tree, it moves HEAD, swaps the lower layer, and regenerates the index, all
  without touching blobs.

### Worktrees

`git worktree add` runs a full checkout, which batch-fetches every blob
(roughly the 275 MB tarball for Linux) and writes it to a real directory. It is
correct but not virtual, and no hook fires early enough to intercept it.
`gvc worktree add <path> <rev>` should run `git worktree add --no-checkout`,
mount a new overlay at `<path>`, and generate that worktree's index. Every
worktree shares the object store and the blob cache, so a new one costs one
mount.

### Push and commit identity

- A commit's id hashes its tree, parents, author, committer, and message. The
  tree id comes from index entries plus the cache-tree extension. Git computes
  all of this locally from blob ids, so unchanged contents never download.
- `git push` from a depth-1 partial clone made zero lazy fetches; the remote
  accepted the new ref. `pack-objects` needs the base commit's trees, which the
  bootstrap holds, plus the new objects.
- Push needs history only when the remote lacks the base commits: pushing to an
  empty repo, or across an unrelated fork. GitHub rejects such a push from a
  shallow clone ("shallow update not allowed"). Hydrate first in that case.
- The Git Database API (`POST /git/blobs`, `/trees`, `/commits`,
  `PATCH /git/refs`) could also publish commits. GitHub computes the same ids
  when every field round-trips, but each write costs 5 points and counts
  against the limit of 80 content-creating requests per minute. Use the git
  push protocol.

### Git LFS

LFS fits the overlay naturally. The lower layer shows LFS content wherever the
tree holds a pointer, so nobody runs a smudge step, and git-lfs is optional.

- **Which paths.** A path shows LFS content when two things hold, the same rule
  git-lfs smudge uses: its attributes say `filter=lfs`, and its blob parses as
  a pointer. A pointer is under 1,024 bytes and holds `version`,
  `oid sha256:…`, and `size`. At bootstrap, batch-fetch every `.gitattributes`
  blob and run `git check-attr --source=HEAD --stdin filter` over all paths.
  Then batch-fetch the candidate blobs, which the tree API sizes show are under
  1,024 bytes. Pointer-shaped files outside LFS attributes stay as text;
  SMPTE/rp268-3-a commits one at `refs/1x1.txt`.
- **Reads.** `st_size` comes from the pointer's `size` field, so `ls`, `stat`,
  and `mmap` see the real size before any download. Content comes from the LFS
  batch API (`POST <repo>.git/info/lfs/objects/batch`: 0.25 s, returning a
  signed URL valid for an hour) or from
  `media.githubusercontent.com/media/<owner>/<repo>/<ref>/<path>`. Both honor
  `Range`: a 100-byte read of a 26.6 MB object returned `206` and exactly 100
  bytes. Cache by SHA-256 in fixed-size blocks, so tools that read only headers
  or footers (file(1), zip, Parquet, safetensors) fetch only those blocks.
  Verify the hash once every block is present.
- **Index.** The entry holds the pointer's blob oid, with the content size as
  its stat size, which is what a normal smudged checkout records. `git status`
  stays clean without running the filter.
- **Writes.** gvc registers itself as the LFS filter in `.git/config`
  (`filter.lfs.process`, `filter.lfs.required=true`) and speaks git's
  long-running filter protocol.
  - On clean (`git add`), it hashes the content, stores it, and emits the
    pointer.
  - On smudge, it emits the pointer unchanged. Git writes those pointer bytes
    during checkout, and the lower-layer re-base drops them because they match
    the committed blob, so the path shows content again.
  - Run the re-base from `post-index-change`. It fires on every index write,
    including `git reset --hard`, which runs no `post-checkout`. The same pass
    replaces the pointer size that git recorded with the content size.
- **Push.** A pre-push hook lists the LFS pointers added in the pushed
  commits. It asks the batch API (`operation: upload`) which objects the server
  lacks and uploads those from the local store. Objects that came from the
  server never upload again.
- **Interop.** Keep git-lfs's store layout (`lfs/objects/aa/bb/<oid>`), shared
  across checkouts through `lfs.storage`. Then `git lfs ls-files`, `push`, and
  `fsck` still work for anyone who has git-lfs. Chain to git-lfs hooks if any
  are installed. Read `.lfsconfig` from the shown tree to pick up a custom
  `lfs.url`.
- **Cost.** GitHub bills LFS bandwidth to the repository owner per GiB
  downloaded, so ranged on-demand reads should cost far less than
  `git lfs pull`. I haven't confirmed how GitHub meters ranged reads.
  Full-tree readers still pull whatever they open; `rg` reads LFS-tracked text
  files in full.
- **Other hosts.** GitLab, Gitea, and Bitbucket serve the same batch API, so
  this layer works on any host; only auth differs.

### Read latching

Latching suits the lazy store (Phase 6): a lookup in the lazy store blocks until that object
arrives, whether from an on-demand fetch or from background hydration. Before Phase 6, `.git` is a real directory, so latching
holds each working-tree lookup only until its directory's listing arrives. Latching the whole `.git` behind a full clone would stall every
command, because every command that parses commits reads `.git/shallow`.

## Choosing channels on GitHub

| Channel | Use it for | Measured | Limit |
|---|---|---|---|
| git smart HTTP (partial clone) | All object bytes; batch blob fetches; history | 916 blobs (12 MB) in one fetch: 7.8 s. Single object: ~0.25 s warm, up to 14 s cold on Linux. | Outside the REST quota; abuse limits apply. Advertises `ls-refs=unborn`, `fetch=shallow wait-for-done filter`, `server-option`. No `object-info`, `bundle-uri`, or `packfile-uris`. |
| REST tree API | Paths, modes, oids, **sizes** | Linux root, recursive: 2.3 s, 71,474 entries, truncated | 100k entries / 7 MB per call; 5,000 req/h per user |
| raw.githubusercontent.com | Single interactive file opens | 20 ms CDN hit, 200 ms miss | Undocumented; unauthenticated limits tightened May 2025 |
| REST `git/blobs` (raw) | Fallback blob reads | 0.55 s for 300 KB | Counts against 5,000/h, so bulk use is out |
| Tarball (`/tarball/{sha}`) | Background full hydration | Linux: 275 MB in 39 s (7 MB/s on this link) | Content can differ from blobs (`export-ignore`, `export-subst`): hash each file against its tree oid |
| GraphQL | `blame`, history pages | blame of a 2,070-range file: 3.7 s | 5,000 points/h |
| LFS batch API, media.githubusercontent.com | LFS content, by byte range | Batch call 0.25 s; ranged reads return `206` | 3,000 req/min authenticated; bandwidth billed to the repo owner |
| REST commits/compare | Path history, merge-base | 1.5–1.8 s | 5,000/h |

REST quotas rule REST out as the per-file channel. An editor opening a project
reads thousands of files, and an authenticated user gets 5,000 REST requests
per hour, at most 100 concurrent, and 900 points per minute. Route bulk object
traffic over the git protocol.

## Hard parts

1. **Lazy-fetch storms.** Partial clone fetches a missing object in a separate
   `git fetch` subprocess, costing 0.25–0.9 s each. Any command that reads
   objects in a loop without batching (blame, `log -p` over long ranges,
   `checkout -- path`) becomes minutes long. The lazy store (Phase 6) fixes
   this by batching and reading ahead behind one warm connection.
2. **Full-tree readers.** `rg`, IDE indexers, `npm install`, and builds read
   everything, and no lazy design avoids that. Offer `gvc hydrate`, which
   streams the tarball, or `git backfill` (git 2.49+), which batch-fetches
   blobs. Watch also for prefetch rules that hydrate too eagerly.
3. **Attributes and filters.** Besides LFS (see "Git LFS"), conversions such
   as `eol`/`text`, `ident`, `working-tree-encoding`, and custom `filter=`
   drivers make working-tree bytes differ from the blob. Their output size is
   unknown until the conversion runs. Detect them at clone time, and either
   convert on first `getattr` (`git cat-file --filters`) or refuse.
4. **Shallow-window correctness.** Until history hydrates, `merge-base`,
   `rebase` onto old bases, and `describe` give wrong answers or fail. Hold
   those commands until hydration finishes, or use the lazy store.
5. **Offline.** Reads of unfetched blobs fail with `EIO`. Report this clearly
   and offer to pin paths.
6. **Platforms.** Linux FUSE is solid. On macOS, gvc's FSKit extension serves
   the same `Filesystem` implementations through a Swift shim; macFUSE, FUSE-T
   and a local NFSv3 server, as EdenFS uses, are the alternatives.
   Windows needs ProjFS, which VFS for Git used. Containers need `/dev/fuse`
   and either `CAP_SYS_ADMIN` or a user namespace.
7. **Git-version drift.** The lazy store depends on git's syscall patterns:
   direct opens of loose objects, `access()` probes on writes, and readdir for
   abbreviations. Pin a tested git range and run a syscall-trace test in CI.

## Backend interface

The git protocol is the same on every host. Make it the base backend and add
host APIs as optional capabilities:

```go
type Backend interface {
    ResolveRef(ctx context.Context, ref string) (OID, error)
    // Exact object bytes. Batched; supports filter and deepen.
    FetchObjects(ctx context.Context, want []OID, opt FetchOpts) (ObjectIter, error)
    ListTree(ctx context.Context, tree OID, recursive bool) ([]TreeEntry, error) // mode, name, oid
}

// Optional accelerators, discovered by type assertion.
type BlobSizer interface{ BlobSizes(ctx context.Context, tree OID) (map[OID]int64, error) }
type Blamer    interface{ Blame(ctx context.Context, rev OID, path string) ([]BlameRange, error) }
type PathLog   interface{ PathHistory(ctx context.Context, rev OID, path string, n int) ([]OID, error) }
type Snapshot  interface{ Tarball(ctx context.Context, rev OID) (io.ReadCloser, error) }
```

Without `BlobSizer`, the daemon fetches a blob on first `getattr`, and fsmonitor
keeps `git status` from stat-ing everything. GitLab and Gitea also serve git
over smart HTTP; confirm each host advertises `filter` before you rely on
partial clone there.

## Prior art

- **VFS for Git (Microsoft).** This is the closest prior art: a lazily
  hydrated git working tree, built for the Windows OS monorepo. It needs three
  things this design avoids. It runs only on Windows, through ProjFS. It needs
  a server that speaks the GVFS protocol, which in practice means Azure Repos;
  GitHub returns 404 for `/gvfs/config` and `/gvfs/sizes`. And it needs the
  `microsoft/git` fork. Its README recommends Scalar for new deployments, while
  the Windows repo stays on VFS for Git. The `post-index-change` hook came
  from this work.

  | | VFS for Git | gvc |
  |---|---|---|
  | Git client | `microsoft/git` fork | Stock git |
  | Server | GVFS protocol: `/gvfs/objects` (with `commitDepth`), `/gvfs/prefetch`, `/gvfs/sizes`, cache servers | Git protocol v2 partial clone (any host), plus host APIs for sizes and blame |
  | OS layer | ProjFS. Files hydrate into real NTFS files and then bypass the provider | FUSE. Every operation passes through the daemon; passthrough covers edited files |
  | Untouched files | A fork-only virtual-filesystem hook makes git skip them, like skip-worktree | Generated index with matching stat data, plus the fsmonitor hook |
  | `git checkout` | Fast: git skips untouched paths, and ProjFS re-projects | Git writes changed files, so cost grows with the diff; `gvc switch` gives an instant switch |
  | Touched files | Stay on the modified-paths list, so `status` slows as it grows until `gvfs dehydrate` | Re-base drops upper files that match the new HEAD |
  | History | Hourly prefetch packs of commits and trees | Background blobless fetch, or the lazy object store |
  | Daemon crash | Hydrated files stay readable | Mount fails with `ENOTCONN`, so the daemon must restart and recover |

- **Scalar (Microsoft, in git since 2.38).** It combines blobless partial
  clone, cone-mode sparse checkout, fsmonitor, and background maintenance, with
  no virtual filesystem. Microsoft moved its Office monorepo to it because
  Apple deprecated the kernel features VFS for Git needed on macOS, and because
  Office's build graph knows which files a build needs. A virtual checkout
  pays off when nobody knows the needed set up front, as with agents and
  ad-hoc tools. gvc is Scalar's upstream foundations with a FUSE projection
  where Scalar uses sparse checkout.
- **EdenFS (Meta).** It runs on FUSE on Linux, NFSv3 on macOS, and ProjFS on
  Windows. It includes a `GitBackingStore`, but the git CLI knows nothing of
  EdenFS, so `git status` and `checkout` don't benefit. This design closes
  that gap with the generated index, the fsmonitor hook, and the lower-layer
  re-base.
- **Scion (Anthropic).** Its virtual checkouts "materialize files on demand."
  The client negotiates by trees and blobs it wants, and servers answer
  history, blame, merge-base, and diff through APIs. Commits happen
  server-side, "so there's nothing to push." This design keeps git's local
  commit-and-push model and borrows Scion's on-demand reads and API-served
  history queries.

## Open questions for a prototype

- Does git accept a lazy-fetch response that carries more objects than it
  asked for? If so, a local promisor proxy could answer the first miss for a
  path with every version of that path, giving batched prefetch before the
  Phase 6 store exists.
- How large is a blobless or treeless full-history fetch of Linux? It decides
  which repos hydrate (Phase 4) and which need the lazy store (Phase 6).
- Does raw.githubusercontent.com hold up as an authenticated channel at bulk
  volume?
- Do git's object-lookup syscalls stay stable from 2.40 to 2.53 under a FUSE
  alternate?
- How fast is `git status` on a 97k-entry FUSE tree with and without fsmonitor?
  (Expect O(changes) with it.)
